## 1. 三条链路的「带宽」不是一回事（最容易反复混淆的一点）

| 链路 | 通道 | 量级 | 带宽性质 | 消费者 |
|---|---|---|---|---|
| 官方图传 | 图传模块 → 硬件无线专线 → 选手端 **和自定义客户端（UDP 3334）** | Mbit/s 级，HEVC 1080p60 | **硬件专属，不用你管**（不是"不受限"） | 人眼 |
| 裁判系统数据 | RJ45 + MQTT 3333 / Protobuf | 协议未给字节上限，只约束各 message 频率 | 裁判系统白送，位姿 1 Hz 写死在协议 | 程序 |
| 自定义 UI 0x0301 | 串口绘图指令 → 在选手端界面上叠加 | 3720 B/s × λ（雷达/哨兵 5120） | **全篇唯一真正紧张的带宽**，与机器人间通信共享 | 人眼 |
| 0x0310 / 0x0311 | 图传链路 VTM Link（**与 1080p60 共享物理链路**） | 300 B@50 Hz / 30 B@75 Hz | 图传链路的大头给了画面，自定义数据吃余量 | 人眼 / 程序 |

**两个必须记住的修正：**

- **自定义客户端不用打"压片战争"。** 协议第 2 章原文：`图传 | UDP 3334，客户端做服务端。HEVC 1080p60` ——
  自己程序收到的画面和官方选手端**同源同画质**。
  "压片战争"专指 **0x0310 那 15 KB/s 上比谁压得狠**（代表：东南大学 `github.com/ElainaXD/rm_compress`，
  192×192@24fps、560 B/帧、CompressAI + TensorRT 超分到 384×384，原文自述"画面确实比较模糊，但可以用于吊射矫正"）。
- **0x0310 不是独立通道**。协议指令概览表标注 0x0309/0x0310/0x0311 均走**图传链路**，
  与 3334 的 1080p60 共享同一条物理无线链路。它独立于 MQTT 数据链路，不独立于图传链路。

## 2. 规则依据（原文，非二手解读）

### 2.1 §5.7 自定义客户端 —— 定位与官方示例

> 自定义客户端是参赛队伍自制的一套多用途设备，用于接收裁判系统赛事引擎服务器发送的比赛相关信息与机器人图传画面，
> 并向赛事引擎服务器发送赛事专用交互指令，**以拓展人机交互可能性**。
>
> **示例：某队伍制作了自定义客户端，能够接收机器人图传并在自制显示器上呈现，同时叠加通过非官方链路显示的自制UI，
> 并通过自定义控制器或自制手柄对机器人进行操控。由此，该队伍无需使用官方裁判系统选手端亦能完成比赛。**

⇒ 「用自定义终端 + 自制 UI 替代官方选手端」是规则**明确举的正面示例**。

### 2.2 唯一红线：己方可获取

> 自定义客户端可以接收**裁判系统选手端显示且己方可获取**的赛事信息

| 想传的东西 | 判断 | 理由 |
|---|---|---|
| 自瞄锁定状态 / 锁定目标 / 距离 / 开火时机 | ✅ 合规 | 己方机器人自身状态，操作手本来也看得见 |
| 车载视觉测出的**敌方全局位置** | ❌ 不要做 | 绕过雷达体系（雷达是官方唯一敌方定位手段，带 P 进度与 d<0.8/1.6 m 误差等级） |

### 2.3 遮挡/中断时各渠道的可用性（之前"表述冲突"的结案）

| 场景 | 图传 | 小地图 | 自定义 UI(0x0301) | 自定义客户端 |
|---|---|---|---|---|
| 超热量断图传 §5.1.3 | 断 | 可用 | **可用** | — |
| 英雄部署模式 §5.6.1 | 断 | 可用 | **可用** | **自定义数据流不受影响** |
| 飞镖命中 §5.6.5 | — | 位置被遮挡 10/5/3/2 s | **被遮挡**（与选手端同步） | **仍可正常接收** |
| 黄牌警告 | 不可用 | 不可用 | **不可用** | — |

⇒ 自定义 UI **不是**全场景兜底（飞镖命中、黄牌时一样被遮）；
**真正稳的是自定义终端**，飞镖命中期间它不受影响。

### 3.1 电控侧实测状态（2026-10-25 复核）

- `bsp_referee_UI\`：`UI_print.c/h`、`Referee_system.c/h`、`BSP_CRC.c`、`fifo.c` 均在，
  `UI_print.c` 已编译进 `rtthread.elf`（`.obj` 存在）。
- **真实调用点 = 0**：剔掉注释后，`DrawLine` / `DrawRectangle` / `DrawCircle` 各 0 次；
  `uiDrawString` / `uiRefresh` 命中的几处全部是 `UI_print.h` 里的**函数声明**。
  `Referee.c` 里现存的写法是 `//// uiDrawFloatDataSeq("005",...)` 这种被注释的示例。
- `Referee.c` 238 行全是注释，**但它不是接收主流程**：真正的接收在
  `bsp_referee_UI/Referee_system.c::referee_thread_entry`（USART6 115200 初始化 → `Referee_system_Init` →
  双缓冲 DMA 解包 → 发布 `robot_status` / `power_heat_data`），代码完整，`rtconfig.h` 也开了 `BSP_USING_REFEREE_TASK`。
- **真正卡住的是 `src/task/robot.c` 一行**：线程 `rt_thread_create("referee", ...)` 了，但
  `rt_thread_startup(referee_thread_handle);` 被注释 —— 而且注释后 `if (handle != RT_NULL)` 没了函数体，
  会把下一条语句吃进 if（这里下一条恰好是 `#endif` 后的 `return RT_EOK;`，碰巧无害，恢复时要留意）。
- ⇒ 前置工作是"问清为什么注释掉（串口冲突？）→ 放开这一行"，不是重写接收流程。之后再接绘制。

### 3.2 0x0301 离线预览（不碰 C 板也能调排版）

- `tools/ui0301_host/build.py`：用 MSVC 在 PC 上编译电控仓库**原样的** `UI_print.c` + `BSP_CRC.c`（只打桩 HAL/RT-Thread），
  `harness.c` 按固件的调用顺序画图，`HAL_UART_Transmit_DMA` 改写到 `out/frames.bin`。
- `tools/ui0301_preview.py frames.bin -o ui.png [--bg 截图.png]`：解析 0xA5 帧，校验 CRC8/CRC16、Data_Length、
  sender↔receiver、图层/颜色/坐标/字号范围、“修改了没增加过的图形”，按选手端坐标系（左下原点 1920×1080）出图，
  并给出字节预算。同样能吃 USB 转串口抓的 UART6 TX 原始字节。
- 已验证：结构体大小与协议一致（图形 15 B、字符 45 B、帧头 7 B），库生成的 11 帧 CRC 全对。
- **对库的实测结论**（给电控）：
  1. `uiDrawGraphics` / `uiDrawIntData` / `uiDrawStringData` / `uiDeleteGraphic` 等**直接版函数不会发任何字节**
     （`UI_SendByteS` 全被注释）。只有 `ui*Seq` + 自己遍历 `UI_SendTCBSequence` 调 `UI_Draw()` 这条路能用。
     另外 `uiDeleteGraphic` 只有直接版，**删除图层目前发不出去**。
  2. `uiRefreshStringDataSeq` 用 `sizeof(chardata) - 1` 当长度（指针大小，ARM 上 = 3），
     刷新后的字符串**只剩前 3 个字符**；PC 上 64 位指针下截成 7 个（预览图里 "REFRESH"）。应改成 `strlen(chardata)`。
  3. 刷新函数里 `NowTCB->frequency = frequency;` 没像创建时那样 `/10`。仓库里没有使用 `frequency` 的调度器，
     影响取决于电控之后怎么写调度，写的时候统一单位即可。

## 4. 缺口清单

### 4.1 客户端 · 功能缺口（数据收到了但没画）

`client_link.py` 订阅 25 个 topic，`operator_ui.html` 只绑定 9 个。**16 个消息一直收到但 UI 零引用**：

| 消息 | 本该干什么 |
|---|---|
| `Event` | 比赛关键事件播报（操作手最需要） |
| `PenaltyInfo` | 黄牌 / 红牌 / 超功率 / 超热量 |
| `Buff` | 当前增益 + 剩余时间 |
| `RobotModuleStatus` | 模块离线告警 |
| `RuneStatusSync` | 能量机关状态 |
| `DartSelectTargetStatusSync` | 飞镖目标与状态 |
| `AirSupportStatusSync` | 空中支援剩余时间 |
| `DeployModeStatusSync` | 部署模式 |
| `SentryStatusSync` / `SentryCtrlResult` / `RobotPathPlanInfo` | 哨兵控制与路径 |
| `GlobalSpecialMechanism` / `RobotInjuryStat` / `TechCoreMotionStateSync` | 特殊机制 / 伤害统计 / 科技核心 |

**这一块性价比最高：数据已在手上，纯前端。**

### 4.2 客户端 · 其他缺口

- 场地图只有 2m 网格 + 红蓝底色 + 本机点 + 雷达点 + 标记叉，**无场地几何底图**（高地/围挡/通道/补给站）
- 全图机器人显示不了（只有本机 `RobotPosition`，敌方全靠雷达点）
- **网页端无手柄**（代码里的 Xbox 手柄说明是给模拟器的，不是终端）；键位写死在 `RMU_KEYS`
- **无录制复盘**
- 诊断区只有 4 行纯文字，无延迟/丢包/码率面板

### 4.3 客户端 · 真机风险（一项未验）

1. `RadarInfoToClient` 字段布局（手册无字段号，现按 `robot_info = 1`、12 组推测）——**错了整体错位**
2. `MapClickCmd/Info` 坐标单位与场地尺寸、字段 3/6 的 mode/type 语义
3. 鼠标增量 / 滚轮 `mouse_z` / 灵敏度是否符合固件预期
4. 真实 1080p60 HEVC 端到端解码性能（浏览器 H.265 支持）
5. `0x0310` 真机未接（仿真走 MQTT 直发，真机要走串口）

## 5. 下一步计划

### P0 · 半真机联调（最高优先，能一次清掉 4 项风险）

**前置阻塞：本机没有引擎要的 IP。** 引擎日志停在 IP 自检，探测到的网卡地址是
`10.201.129.98` + 一堆 `169.254.x.x`（DHCP 失败），**没有 `192.168.1.2`**。

步骤：

1. 给当前网卡加**二级 IP** `192.168.1.2/24`（不动现有配置，避免断网）
2. 重开 `RoboMasterEngine.exe`，在登录页点「本地ip配置测试」应通过
3. 走完登录 → 进主界面 → 建房间/进比赛
4. 两个网段不是一回事，已按官方《自定义客户端配置说明手册》确认：`192.168.1.2` 是**选手端连引擎**的网卡；
   `192.168.12.1:3333` 是**选手端**自己开的 MQTT 服务，自定义客户端（`192.168.12.2`）连的是选手端不是引擎。
   10-22 实测：选手端本机确实监听 3333，未登录服务器时拒绝连接（日志"选手端未登录服务器"）。
   单机测试连 `127.0.0.1:3333`，clientID = 选手端登录的机器人 ID。
   **未知**：没有真车时引擎是否允许选手端以某 ID 登录、会推哪些 topic——可能只能验到 `GameStatus`。
5. 我们的客户端连上去，看实际收到哪些 topic（没有机器人时可能只有 `GameStatus`）
6. 逐项验证：连接参数与 clientID 规则 → topic 命名 → `RadarInfoToClient` 布局 → `MapClick` 往返

**预期收益**：把"只在仿真成立"的假设压到最低，尤其 `RadarInfoToClient` 这条最容易现场咬人。
