# 无 ROS 窄带 H.264 接入实验

本实现独立编写，参考 ACE 开源的 H.264/300B 包/限频/IDR恢复思路，未复制其代码，
也不与 ACE 线上包格式兼容。无需 ROS，不改变 deploy_dev 推理链和 ROI。

## 启动

Python 3.11+，依赖 `pip install av Pillow`（PyAV 需包含 libx264 编码器）。
Windows/Linux/macOS 使用相同的 `python tools/operator_web.py`。
测试：`python tools/test_narrowband_video.py`。
本次实际运行平台只有 Windows，其他平台尚未实测。

环境变量 `DAEDALUS_VIDEO_SOURCE` 可指定任意 HTTP JPEG 快照源，默认
`http://127.0.0.1:5000/snapshot/raw`。Windows 现有源由 Web 桥提供；
跨平台的是编解码、分包、限速、页面测试链，源适配器需在对应平台提供。

打开 `http://127.0.0.1:5002/`，点击“应用 H.264 测试配置”。可选择40/80kbit/s、
40/50包每秒、0/1/3/5%随机丢包，并在JPEG与H.264解码结果之间切换。

## 数据链

快照→保持全视野的320×240 letterbox→libx264（veryfast/zerolatency、无B帧、2秒GOP）
→300B固定包→每25ms或20ms一个发送槽→随机丢包→整帧重组→H.264解码。
浏览器获取解码结果转成的JPEG，展示转换的字节不计入窄带码率。
HTTP源已经是JPEG，因此这不是原始无损图像编码基准。

测试包头为网络序 `!IHHHBB`：帧号、分片号、分片数、有效长度、关键帧标志、版本。
12B头、最多288B数据、填充至300B，整个300B计入发送预算。
这模拟裁判自定义载荷，不计裁判串口外层开销，也没有真实MQTT/串口接入。
队列只容纳一帧等待单元，拥堵时跳过尚未编码的输入，不任意丢弃参考帧。
发现不连续则重建解码器，等待IDR恢复。此版本不包含FEC/重传。

## 指标含义

- encoded_kbps：实际产生H.264字节的平均码率，不是配置目标值。
- wire_kbps：包括测试包头/填充/被丢弃包的发送平均码率，40Hz上限96kbit/s。
- decoded_fps：解码帧数，不代表相机独立帧数。
- changed_snapshots：收到的不同JPEG字节数量；静态相同画面也可能不增加。
- pipeline_ms：请求源前到解码完成，包括本测试编码、排队、发送；不含源自身采集延迟及浏览器显示。
- decoded_age_ms：距最近解码输出时间，冻结时持续增加。
- last_recovery_ms：第一次模拟丢包到下次成功解码的时间。

## 2026-09-19 Windows 接入结果

单元测试验证60帧完整编码/分包/解码，并验证丢分片后在后续IDR恢复。
实际HTTP源接入：320×240/12FPS目标/80kbit目标/40Hz。

| 场景 | H.264平均 | 含头填充平均 | 解码FPS | 最近链路延迟 | 最近丢包恢复 |
|---|---:|---:|---:|---:|---:|
| 无丢包 | 26.73 kbit/s | 39.59 kbit/s | 9.37 | 63ms | — |
| 3%随机丢包短测（实际10/226包） | 32.98 kbit/s | 45.56 kbit/s | 3.44 | 297ms | 2156ms |

当时源画面变化极少（分别仅2/1种快照），故这些结果只证明接入与恢复机制工作，
不能据此宣称运动场景画质/驾驶延迟达标。下一步需动态录像或连续运动源，
同源比较目标可辨认程度、延迟分位数和冻结时长；尤其验证2秒GOP下丢包冻结。
