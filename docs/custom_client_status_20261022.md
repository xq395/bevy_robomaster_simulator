## 0. 结论

1. **自定义终端（网页客户端）已经做完**，在 Mock 和仿真上全部验证通过，**没有上过真实裁判系统**。
2. **自定义 UI（官方选手端渲染）没有做**，而且不该由这条线做——它写在 C 板（STM32），本仓库里 `0x0301` 相关代码为 0 处。电控侧有完整的绘图库 `UI_print.c`（约 1300 行），但**全工程没有任何调用点**，`referee_task.c` 里连裁判系统初始化都是注释掉的。
3. **两者是两条独立链路**，走不同物理通道、不同协议，带宽互不占用，可以并存。这不是"二选一"。
4. **对考核而言**：那 5 分考的是自定义终端的交互功能，选手端上的 UI 不算分 → 没必要做。
   **对实战而言**：UI 有价值且便宜（1–2 天），但属于电控的活，建议移交。

## 1. 两条链路的分界（这是最容易混的一点）

| | 自定义 UI | 自定义终端 |
|---|---|---|
| 本质 | 让**官方选手端**在它自己的界面上叠加几笔图形 | 自己做**整台设备**：显示 + 运算 + 输入 + 软件 |
| 物理通道 | 机器人主控 → 串口 `0x0301` | RJ45 + MQTT 3.1.1 / ProtoBuf，图传走 UDP 3334 |
| 代码位置 | **C 板（STM32）**，不在本仓库 | `tools/operator_web.py` + `tools/rmu_protocol/*` |
| 提供什么 | 只有"画什么"的指令（15 B/图形） | 显示、交互、键鼠、指令下发 |
| 带宽 | 3720 B/s ×λ（雷达/哨兵 5120），**与机器人间通信共享** | 独立通道，另有 0x0310 图传 15 KB/s 上限 |
| 能否显示图传 | **不能**（只有 8 种矢量图 + 数字 + 字符串） | 能（27–28 fps HEVC） |
| 能否交互 | **不能**（单向） | 能（键鼠 75 Hz、指令 ≤10 Hz） |
| 图层上限 | 10 层，动不了选手端排版 | 无 |
| 飞镖命中 / 黄牌 | 会被遮挡（10/5/3/2 s） | 仍可正常接收图传数据 |

一句话区分门槛：**自定义 UI 的门槛是"会写串口发包"，自定义终端的门槛是"会做桌面应用"。**

## 2. 自定义终端：已经做到哪一步

### 2.1 能力清单（已实现）

- MQTT 3.1.1 + ProtoBuf 收发裁判数据；UDP 3334 收 HEVC 图传
- 0x0310 自定义数据流图传：H.264 intra-refresh，300 B × 50 Hz，约 15 KB/s（第二视角 / 图传中断兜底，默认不选中）
- 0x0311 上行控制（30 B，≤75 Hz）
- 键鼠下发按 75 Hz 定频、指令白名单 + 字段校验 + 手册限频
- 接管互斥：只有明确"接管"才发键鼠；250 ms 无输入自动改发零帧；MQTT 断开 / 页面隐藏 / Esc 撤销接管并清零
- 写接口同源校验（跨源 403）

### 2.2 实测数字（2026-10-22，RTX 4060 笔记本，仿真 1440×1080）

| 项 | 旧（经桥接 JPEG） | 现在 |
|---|---|---|
| 官方图传 3334 | 4–10 fps | **27–28 fps**，960×720，~1.5 Mbit/s，残帧 0 |
| 0x0310 画面 | 无 | **15 fps**，384×288，85–92 kbit/s，41–45 块/s，丢块 0 |
| 键鼠 → 仿真 | — | 鼠标转云台 0.26 rad；按住左键 1.2 s 开火 13 发 |

3334 的瓶颈原来在桥接"每帧 JPEG 编码 44 ms + 取帧 34 ms"串行，现在取帧、缩放转 YUV、编码拆成三条线程；HEVC 编码本身不是瓶颈（hevc_nvenc 稳定 5 ms，libx265 有 30–40 ms 尖峰）。**吞吐最终由取帧决定**（仿真要等下一渲染帧再读回 6 MB）。

### 2.3 验证覆盖

- 27 项单元/集成测试（含 0x0310 块格式、预算、丢块、发送端重启）
- 浏览器端到端 28 项（对 Godot 仿真实测）+ 另有 23 项（HUD、3334、75 Hz、零帧、限频、地图点击、跨源拒绝）
- 协议逐字段与手册比对 + 线上字节回环（`rmu_protocol/verify_proto.py`）

## 3. 自定义终端：未验证项与风险（这是真正的问题清单）

按"会不会在比赛现场咬人"排序：

| # | 风险 | 现状 | 影响 |
|---|---|---|---|
| 1 | `RadarInfoToClient` 字段布局 | 手册无字段号，现按 `robot_info = 1`、12 组处理 | HUD 上雷达信息可能整体错位，**现场才发现** |
| 2 | `MapClickCmd/Info` 坐标单位与场地尺寸，字段 3/6 的 `mode`/`type` 语义 | 按推测实现 | 地图点击可能下发到错误坐标，属"能点但打错"类故障 |
| 3 | 鼠标增量 / 滚轮 `mouse_z` / 灵敏度是否符合固件预期 | 只在仿真上调过（`--mouse-yaw/--mouse-pitch`） | 真机手感不对，操作手会当场弃用终端 |
| 4 | 真实 1080p60 HEVC 端到端性能 | Mock 的编码端是瓶颈，不是解码端 | 真机可能卡在解码或 JPEG 转换 |
| 5 | 键位写死在 `operator_ui.html` 的 `RMU_KEYS`，无手柄 | 未做 | 现场改键位要改代码 |
| 6 | 链路状态只有一段文字（延迟/丢包/帧率/码率无面板、无报警） | 未做 | 出问题只能靠感觉判断 |
| 7 | 无录制与复盘 | 未做 | 赛后无法复现故障 |
| 8 | 0x0310 真机未接 | 仿真里发送端直接发 MQTT；真机要把 `custom_video.Sender.publish(block)` 换成经串口发 `0x0310` | 这条链路目前只在仿真成立 |

另外两条**背景变化**，不是 bug 但会影响优先级：

- **2027 规则取消了部署模式**，`0x0310` 传画面不再是刚需，降级为"第二视角 / 图传中断兜底"。
- 规则解读里提到飞镖命中期间选手端界面/小地图/自定义 UI 都会被遮挡，但关于"自定义终端是否也被遮挡"的表述前后不一致（一处说终端仍可正常接收图传，另一处又说"视觉组的自定义 UI 在这 10 秒里是操作手的唯一眼睛"）。**建议拿原文核对**，这直接决定"UI 作为兜底"这条价值成不成立。

## 4. 自定义 UI：为什么不做，什么情况下才做

### 4.1 查到的现状

- 本仓库（`bevy_robomaster_simulator`）：**没有任何 `0x0301` 相关代码**。
- 电控仓库 `D:\HNU_RM\代码栈\EC\rm\src\modules\referee\bsp_referee_UI\`：`UI_print.c` 1300 行，画线、矩形、圆、圆弧、整数、浮点、字符串、删图层都有。
- 但除了库文件自身，**没有一处调用** `uiDraw*` / `uiRefresh*`；`referee_task.c` 里裁判系统初始化那一行是注释掉的。
- 结论：**库在，没接上，选手端上现在什么都不会画。**
- 注：以上是本机这份代码的状态，队里若有更新分支需另行确认。

### 4.2 三种目标下的结论

| 目标 | 结论 |
|---|---|
| 考核那 5 分 | **没必要**。考的是自定义终端的交互功能，选手端 UI 不算分 |
| 实战辅助 | **值得做，且便宜**。准星、热量条、自瞄锁定状态、超级电容余量这类"机器人自己就知道"的数据画在选手端上，操作手不用多盯一块屏。库已有，接上去约 1–2 天，主要成本在排版和测试 |
| 自定义终端不可用时 | 想法成立，但受上面"遮挡表述冲突"影响，需先核对规则原文 |

### 4.3 工程细节里的坑（给电控的提醒）

- 图形名是 3 字节**索引**，同名"增加"**不会显示**（2019 官方答疑），要改成"修改"。
- 静态元素"增加"一次后就持久，之后只用"修改"刷新数值——**不需要每帧重发静态图**，30 Hz 的限制因此宽松很多。
- 结束后要发 `0x0100` 删除全部，否则下一场残留。
- 3720 B/s 是**自定义 UI 与机器人间通信共享**的，2027 又按 λ 砍，两边要分配。

## 5. 建议

**P0｜移交电控，不在客户端这条线做。** 最小可用版：准星 + 2–3 个数值（热量、电容、自瞄状态）。先"增加"画一次静态元素，之后只"修改"刷数值，刷新频率压在带宽之内。需要的话可以先出一份接入说明（哪个任务里调用、发哪些图层、刷新频率怎么定）。

**P1｜真实裁判系统联调（我们这边）。** 顺序：只连不收发 → 核对 HUD/ID/阶段 → 单独验证图传 → 再逐项验证键鼠与指令。这一步能一次清掉上表 1–4 项风险，是当前最高性价比。

**P2｜键位可配置 + 手柄、链路状态面板、录制复盘。**

**不建议做**：为了"在选手端上画东西"去动客户端这条线——它们在物理上就是两台设备。

## 6. 附：与命中率工作的关系

两条线互不影响。命中率那部分本轮已收口：状态源 + 理想角点 78.8%（288 发，±4.7），图像 + 理想角点 66%，图像 + rp0526 44–56%（小样本）。离 80% 剩下的差距来自取帧时延（约 20–30 ms，丢 13 个点）和 rp0526 角点精度（丢 10–20 个点），详见 `tools/rm_aim_sim/README.md` §6.6。
